# ЛР4: контрольные вопросы

- **Аутентификация** — проверка личности (email и пароль). **Авторизация** — проверка права на действие (например, удалить можно только свою карточку). **Идентификация** — указание, кто обращается, например email.
- **Cookie** — значение, которое браузер хранит для сайта и автоматически отправляет в заголовке `Cookie`. Сервер задаёт её через `Set-Cookie`. `HttpOnly` закрывает чтение из JavaScript, `Secure` ограничивает передачу HTTPS, `SameSite` ограничивает отправку в межсайтовом контексте. Cookie сама по себе не является сессией.
- **Сессия** — состояние входа на сервере. В проекте браузер хранит только подписанный случайный id, Redis — пользователя. Вход меняет id, выход удаляет состояние, TTL ограничивает срок действия. В отличие от прежнего singleton, данные разных запросов не смешиваются.
- **Redis** — быстрое хранилище ключ–значение с TTL. В проекте `asteroids:sess:<id>` хранит JSON с пользователем и cookie. `GET` читает JSON, `TTL` показывает оставшееся время. AOF и Docker volume позволяют сохранять данные при перезапуске; TTL продолжает ограничивать срок сессии.
- **JWT** — формат токена с заголовком, payload и подписью. Payload обычного подписанного JWT читается без секрета: подпись не шифрует данные. Сервер проверяет подпись, срок действия и ожидаемые claims. Немедленный отзыв до истечения срока требует дополнительного состояния, например blacklist в Redis. По заданию JWT/blacklist нужен для Go; здесь выбран NestJS и серверные сессии.
- **SSO** — единый вход в несколько приложений через доверенного провайдера идентификации. Например, OpenID Connect поверх OAuth 2.0 позволяет приложению получить подтверждение личности; OAuth 2.0 сам по себе посвящён делегированию доступа.
- **Двухфакторная аутентификация** — два разных фактора: знание (пароль), владение (TOTP-приложение, аппаратный ключ), биометрия. Два пароля не являются двумя факторами. В этой лабораторной реализован один фактор — пароль.
- **RSA** — асимметрический алгоритм с открытым и закрытым ключами. В схеме подписи закрытый ключ подписывает, открытый проверяет; RS256 в JWT использует RSA с SHA-256. Подпись подтверждает целостность и подлинность, а не скрывает payload. В проекте пароли хешируются scrypt, cookie подписывает библиотека express-session; RSA для реализации выбранного варианта не требуется.
- **Хеширование пароля** — одностороннее вычисление, а не обратимое шифрование. scrypt с уникальной солью затрудняет массовый перебор; при входе вычисляется производный ключ и сравнивается с сохранённым с помощью `timingSafeEqual`.
